# The docs/ tree — what each folder is for

Create these, even empty, on day one — the shape matters more than the
contents at first:

```
docs/
├── superpowers/
│   ├── specs/   # brainstorming output — the WHY and WHAT, one file per initiative
│   ├── plans/   # writing-plans output — the HOW, sequencing, task lists —
│   │            # PLUS the two tracker files (LEDGER.md, REV-TRACKER.md)
│   └── refs/    # supporting screenshots / flow captures a plan cites
├── claude-memory/   # git-mirrored copy of Claude's own memory (see below)
├── runbooks/        # durable operational procedures — branch protection,
│                    # backup/restore, monitoring setup — anything where
│                    # getting it wrong is expensive and the reasoning
│                    # needs to survive whoever set it up
└── findings/        # dated root-cause write-ups — the paper trail
                      # systematic-debugging leaves behind
```

One more directory is generated by the tools themselves and should
**not** be hand-authored: `.superpowers/sdd/<slug>/` — the
`subagent-driven-development` skill's own audit trail (task briefs,
task reports, diff-scoped reviews, a running progress file) while it
executes a plan. Don't scaffold it; it appears on its own.

## `docs/claude-memory/README.md`

Drop this file inside the newly-created `docs/claude-memory/` folder:

```markdown
# Claude memory backup

Version-controlled mirror of Claude's own project memory. Restore from
here if the live copy on a single machine is ever lost.
```

That's the whole point of the folder: Claude's typed long-term memory
(what it learns about the user, the project, and its own past feedback)
lives on local disk by default. This directory is what a Stop hook
(see `backup-hook-template.sh`) mirrors it into, so the memory survives
losing one laptop.
